02 · Paso a paso

Qué ejecutar, desde dónde y qué esperar

Cada bloque parte del resultado anterior. No avance si el resultado esperado no coincide con su terminal.

01

Preparar el repositorio local

Antes de comenzar
Abre una terminal en la carpeta raíz del proyecto. El remoto debe estar vacío; si ya tiene commits, usa git clone.
Ejecuta
git init
Qué hace
Crea la carpeta interna .git, donde Git guardará el historial, las ramas y la configuración.
Resultado esperado
La terminal confirmará la inicialización. git status muestra que estás en un repositorio, aunque todavía no existan commits.
02

Conectar y comprobar el remoto

Antes de empezar
La raíz del repositorio local recién inicializado.
Ejecuta
git remote add origin <URL_DEL_REPOSITORIO>
git remote -v
git fetch origin
Qué hace
remote add registra la URL con el alias origin; remote -v permite verificarla; fetch descarga referencias sin modificar sus archivos.
Resultado esperado
La URL aparece dos veces, para lectura y escritura. En un remoto vacío, fetch puede finalizar sin mostrar contenido.
03

Crear el primer commit en main

Antes de empezar
La raíz del proyecto, con un archivo README.md ya creado.
Ejecuta
git switch -c main
git add README.md
git status
git commit -m "docs: add project README"
Qué hace
Crea main, prepara únicamente el README, permite revisar el área de preparación y registra el primer punto del historial.
Resultado esperado
git status muestra el README en “Changes to be committed”; después del commit, el árbol de trabajo queda limpio.
04

Publicar main y crear develop

Antes de empezar
La rama main, con el primer commit creado.
Ejecuta
git push -u origin main
git switch -c develop
git push -u origin develop
Qué hace
-u configura el seguimiento remoto. develop nace desde el commit actual de main, por eso no está vacía.
Resultado esperado
El remoto contiene main y develop. En envíos posteriores será suficiente ejecutar git push.
05

Abrir una rama de trabajo

Elige primero la base
Usa develop para feature/* y release/*. Usa main para hotfix/*.
Actualiza y crea
git switch <RAMA_BASE>
git pull --ff-only origin <RAMA_BASE>
git switch -c <TIPO>/<NOMBRE>
Qué hace
--ff-only actualiza la base sin crear un merge accidental. La nueva rama parte exactamente de ese estado.
Resultado esperado
git branch --show-current muestra la rama nueva. Puede publicarla con git push -u origin <RAMA>.
06

Registrar y entregar cambios

Antes de empezar
Tu rama feature/*, release/* o hotfix/*; nunca trabajes directamente en main.
Ejecuta
git status
git add <ARCHIVO>
git commit -m "<tipo>: <descripción>"
git push
Qué hace
Revisa, prepara, registra y publica un cambio concreto. Evita git add . hasta comprobar qué archivos incluye.
Resultado esperado
El commit aparece en la rama remota y queda disponible para abrir un pull request hacia el destino indicado en el mapa.
03 · Topología

El recorrido completo de una versión

Las líneas sólidas representan la continuidad real del historial. Cada bifurcación tiene un origen y cada integración, un destino explícito.

mapa cronológico de Gitflow · de izquierda a derecha
main: produccióndevelop: integraciónfeature: funcionalidadrelease: estabilizaciónhotfix: corrección urgente
1. Crear la rama establegit switch -c main git switch mainUsa el primer comando solamente para crear main. En trabajos posteriores, el segundo comando permite volver a esa rama.
2. Abrir la línea de desarrollogit switch -c develop git switch developAntes de crearla, asegúrate de estar en main. Usa el primer comando para crear develop y el segundo para volver a ella posteriormente.
3. Desarrollar una funcionalidadgit switch -c feature/<NOMBRE> git switch feature/<NOMBRE>Antes de crearla, asegúrate de estar en develop. El primer comando crea la funcionalidad; el segundo permite volver a esa rama posteriormente.
4. Integrar la funcionalidadPull request: feature/* → developLa unión verde con la línea celeste indica que el cambio vuelve a la rama desde la cual nació.
5. Estabilizar una versióngit switch -c release/<VERSION> git switch release/<VERSION>Antes de crearla, asegúrate de estar en develop. En esta rama solo se corrigen defectos, documentación y metadatos de versión.
6. Publicar y etiquetarPull request: release/* → main git switch main git pull --ff-only origin main git tag -a v<VERSION> -m "Release v<VERSION>" git push origin v<VERSION>La versión estable llega a main. La etiqueta identifica exactamente el commit publicado.
7. Resolver una urgenciagit switch -c hotfix/<NOMBRE> git switch hotfix/<NOMBRE>Antes de crearla, asegúrate de estar en main. El primer comando crea la corrección urgente; el segundo permite volver a esa rama.

main · línea permanente

Contiene únicamente versiones estables. Recibe releases y los hotfixes aprobados previamente en develop.

release/* → main → etiqueta de versión develop → main

develop · línea permanente

Integra el trabajo futuro. De aquí salen feature y release.

feature/* → develop hotfix/* → develop

feature/* · temporal

Parte de develop y vuelve a develop mediante pull request.

develop → feature/* → develop

release/* · temporal

Estabiliza y prueba una versión sin agregar funcionalidades.

develop → release/* → main → tag

hotfix/* · temporal

Corrige producción; la solución se valida primero en develop y después pasa a main.

main → hotfix/* → develop → main

En escritorio, recorré los puntos de izquierda a derecha. En móvil, la misma topología se presenta como rutas explícitas sin desplazamiento horizontal.

05 · Criterio

Antes de continuar

  • ✓Ejecutar git status antes de agregar o confirmar.
  • ✓Actualizar la rama base con git pull --ff-only.
  • ✓Mantener cada commit enfocado en un cambio concreto.
  • ✓Reservar main para versiones estables e integrar mediante pull requests.
